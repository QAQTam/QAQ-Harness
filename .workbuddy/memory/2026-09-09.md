## 工具侧前端契约分析（toolcard 问题）

- 用户提问：为什么前端总设计 toolcard？工具侧到底给了前端什么。分析基于本仓库真源：
  - `crates/qaqh-types/src/tool_result.rs`（ToolResult / ToolStatus 五态 / ContentRef / ToolModelPayload）
  - `crates/qaqh-domain/src/timeline.rs`（TimelineTool / TimelineToolState / TimelineEvent）
  - `crates/qaqh-domain/bindings/qaqh/*.ts`（ts-rs 导出，即前端实际看到的 TS 类型）
- 结论要点（后续给前端写规格时复用）：
  1. 后端契约里**没有「card」这个概念**，只有 `TimelineBlock{kind: Tool}`。card 是前端侧的降级抽象，源于 `name: string + args_json?: string` 的**开放集合 + 无 schema**（19 内置工具 + 未来 MCP 动态工具无法穷举）。
  2. **状态数错配（关键）**：`ToolStatus` 5 态（ok/error/partial/backgrounded/cancelled），投影到 UI 的 `TimelineToolState` 只有 4 态（prepared/running/succeeded/failed）→ backgrounded 与 cancelled 被折叠，只看 state 无法区分「取消」与「失败」，须从 `failure.code` 或 ToolResult.status 反推。**可能需要后端补一态。**
  3. `tool_call_prepared.args_so_far` 是**增量半截 JSON**，前端不能直接 JSON.parse。
  4. 大输出走 `output_ref: ContentRef{content_id, media_type, sha256, truncated}`，需另调 content 下载端点，`output` 只是保留尾巴。
  5. `diff` 只存在于展示平面：`project_for_model()` 与 `render_xml_envelope()` 都不含它（省 token 的刻意为之）→ 模型与前端看到的**不是同一份内容**。
  6. `progress` 语义是 append 到 buffer，不是 replace（TimelineEvent::ToolProgress 由单一 reducer 追加）。
  7. `TimelineToolPermission` 只是展示数据（reason/paths/category/level/risk/consequence）；真正的一问一答走 control 平面 PermissionChallenge（一次性 TTL 凭证），**permission 字段需要 UI 控件而非静态展示**。
  8. 另有 `ToolEvent::code_changed`（lines_added/removed、files_created/deleted）可直接驱动改动统计；`audit_recorded` 供审计抽屉。
- 建议：术语统一为 **tool block**（与 TimelineBlock 对齐），组件按状态机 + patch 实现；渲染按 6 个「档位」而非 19 个组件：读取 / 变更（必带 diff 抽屉）/ 执行（stdout 流 + code_changed）/ 交互（ask_user + permission）/ 后台（可轮询可取消）/ 通用兜底。
- 相关文档：docs/frontend-contract.md（契约真源在本仓库，变更走 RFC 流程）。

## 工具返回管线审查（是否值得重塑）

- 用户提问：工具返回管线（用了四个月、当初随手写的）有没有必要优化。结论：**有必要，但只做「投影收敛」，不做 ToolResult 大手术。**
- 管线实测形状（已逐一读码取证）：
  handler → `ToolResult`（qaqh-types/tool_result.rs，7 字段全可变）→ `tool_side_fold::apply`（qaqh-workspace/execution.rs:117）→ `finalize_req`（manager.rs:435）→ 分叉为 模型面（`render_xml_envelope`）/ UI 面（TimelineTool）/ 内容外置（`externalize_large_content`，registry.rs:737，经 actor.rs:62 调用）。
- **发现的问题（按严重度）**：
  1. **P1 真 bug · 折叠策略进程级全局污染**：`tool_side_fold::set_policy` 改的是 `static LazyLock<RwLock<Arc<dyn ToolResultFoldPolicy>>>`；唯一调用点在 `agent/state/agent.rs:477-485` 的 **per-session** `apply_tool_mode`。daemon 单进程多会话 → 会话 A 切 minimal 会把会话 B 的 exec 输出也变成不截断。修法：`limit_for` 本质是查表纯函数，把 policy 塞进 `ToolCtx` 下传，删全局。（注意：此推断基于代码静态阅读，尚未跑并发验证。）
  2. **P1 契约失真 · output_ref 在标准模式下永不触发**：`CONTENT_STORE_THRESHOLD_BYTES = 10 MiB`（ringing/content_store.rs:15），而标准模式 `model.text` 已被 `TOOL_MODEL_MAX_CHARS = 24_000` 硬顶（≈96KB 上限）。96KB ≪ 10MB → `externalize_large_content` 外置分支只可能在 NoFold 极限模式 + >10MB 时触发。**上一轮给前端的「大输出走 output_ref、需另调 content 下载端点」建议据此撤回。**
  3. P2：`summary`（前 512 字符）/ `model.text`（前 24K）/ `content`（=model_text()，manager.rs:483）是同一份原文的三次投影，但 ToolResult 是可变结构体，字段可独立写（`externalize_large_content` 就同时改了 summary 和 model.text），无不变量保护。
  4. P2：`ToolExecResult{content: String, result: ToolResult}` 双表示并排传（admit.rs:135/137）；`execution.rs:92` 存在从 content 反推 result 的反向构造，说明不变量已在被绕。
  5. P3：`compact_data()`（tool_result.rs:331）静默删除 `stdout`/`stderr`/`output`/`content` 四个 key，工具作者无预期、无编译护栏。
  6. P3：`sha256: content_id.clone()`（registry.rs:772）**不是 bug** —— `ContentStore::put` 用 `sha256_hex(&bytes)` 作 content_id（内容寻址），二者本就相等。已核实，勿误改。
- **建议方案**：`ToolResult` 保留为权威输出（status + 全文 + diff + images + error + 可选 data），把 `summary` / `model.text` / `output_ref` 从可变字段改为**惰性投影函数**（`fn summary(&self)`、`fn project_for_model(&self, limit)`、`fn externalize(&self, threshold)`）。好处：三者不可能漂移（编译期即无法单独改）；外置阈值可按投影面分别配（模型 24K、UI 256KB），不再共用一个 10MB。成本：只改 qaqh-types + 少量调用点，`ToolResult::ok()` 等构造函数签名可不变，19 个工具基本不动。
- **不建议动**：`tool_side_fold` 的策略接口本身（StandardPolicy/NoFoldPolicy 两态语义清晰、白名单注释完备，是这份代码里质量最高的部分）；`edit/` 与 `apply_patch/` 合并（审计已判定是暴露给模型的两个不同工具）；`project_for_model`（JSON）与 `render_xml_envelope`（XML 信封）双形态（服务于不同协议，非冗余）。
- 可独立 commit 的三件小事：折叠策略去全局化、TimelineToolState 补 cancelled/backgrounded 两态、output_ref 阈值重新设计或删路径。
